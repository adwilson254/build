# OpenRivian

OpenRivian brings an openpilot-based driver assistance stack to the **Rivian
R1S / R1T**, running on a **comma 4** device. It layers a small set of
Rivian-specific features (a cloud API client, an MQTT telemetry bridge, a React
web UI, and a driving-scores daemon) on top of upstream openpilot — without ever
hand-editing upstream files in place.

## Fork lineage

OpenRivian sits at the end of this fork chain:

```
commaai/openpilot
  └─ sunnypilot/sunnypilot
       └─ AdventurePilotDev/AdventurePilot
            └─ adwilson254/openpilot   ← this repo (OpenRivian)
```

We track **AdventurePilot** as our direct upstream and continuously merge it
into `main`.

## Branches

OpenRivian uses a strict separation between "source of truth" and "deployable
build".

| Branch | Role | Edited by |
| --- | --- | --- |
| `main` | **Source of truth.** Pure upstream code **plus additive tooling only**: the cleaner + injector scripts, tests, and CI. Never stripped, never carries in-place Rivian patches to upstream files. | Humans (PRs) |
| `ap` | **Deployable build.** Fully generated by CI: upstream merged, web UI built, non-Rivian code stripped, Rivian features injected, then linted + tested. This is what you flash to the comma 4. | **CI only — never by hand** |
| `cleaner-script-final` | Legacy/working branch that originally held the cleaner. Superseded by `main`; kept for history. | — |

> **Never edit `ap` by hand.** It is force-pushed on every successful pipeline
> run, so any manual change will be overwritten and lost. All real work happens
> on `main`; `ap` is a build artifact.

## How the pipeline works

The full **clean → inject → lint → test → promote** flow lives in
[`.github/workflows/sync_upstream.yml`](.github/workflows/sync_upstream.yml). It
runs daily (03:00 UTC) and on manual dispatch.

1. **Merge upstream** — merge AdventurePilot `main` into our `main`, failing hard
   on conflicts so they get resolved by a human.
2. **Track source** — push `main` when upstream advanced.
3. **Build the deployable tree** (on a throwaway branch):
   - build the React web UI bundle (so the injected `dist` matches its
     `index.html`),
   - **strip** non-Rivian code with `scripts/rivian_cleaner.py`,
   - **inject** the Rivian features with the `scripts/features/inject_*.py`
     scripts.
4. **Lint** the Rivian additions for real defects (pyflakes / syntax /
   bare-except classes).
5. **Test** with the fast, pure-Python gate (`tests/antigravity`).
6. **Promote** — only if lint + tests are green, force-push the validated tree
   to `ap`.

The injectors are **idempotent**, so an unchanged upstream produces a stable,
reproducible `ap`.

## Rivian features

All Rivian features are **injected** into the generated `ap` build — they are
never hardcoded into upstream files on `main`. Feature source lives under
`scripts/features/src/` and is copied/patched into place by the injectors in
`scripts/features/`:

| Feature | Source | Injector | What it does |
| --- | --- | --- | --- |
| **Cloud API** | `src/rivian/api.py` | `inject_api.py` | Rivian cloud API client; adds API toggle/login + status to the Developer settings UI. |
| **MQTT bridge** | `src/rivian/mqttd.py` | `inject_mqtt.py` | MQTT bridge/broker daemon that publishes vehicle + cloud telemetry; registered as the `mqttd` managed process. |
| **Web UI** | `src/web_ui/` (React/Vite frontend + `webd.py`) | `inject_web.py` | Serves a React web UI from the device via the `webd` process; validates the built `dist` so a no-JS bundle never ships. |
| **Scores** | `src/rivian/scorerd.py` | `inject_scores.py` | `RivianScorer` daemon computing **Smoothness** and **Path-Accuracy** metrics; registered as the `scorerd` onroad process. |

A shared helper, `inject_common.py`, registers each feature's param keys in
`common/params_keys.h` so features fully own their params while `main` stays
pure upstream. The non-Rivian **cleaner**, `scripts/rivian_cleaner.py`, removes
non-Rivian car ports and uses replacement templates under `scripts/templates/`.

## Development & testing

A podman-based harness lives in [`ci/`](ci/) (works locally with podman or
docker, and in GitHub Actions). See [`ci/README.md`](ci/README.md) for details.
The two tiers:

### Fast gate — `ci/run-fast.sh`

The pure-Python merge gate (no compiled artifacts; runs in seconds). This is
what must be green before `main` is promoted to `ap`. It runs the tests under
[`tests/antigravity/`](tests/antigravity/):

- injector correctness + **idempotency** (`test_injectors.py`)
- the non-Rivian cleaner (`test_cleaner.py`)
- a `process_config.py` import-safety regression (`test_process_config_safe.py`)
- `scorerd` unit tests (`test_scorerd.py`)
- web-`dist` integrity (`test_web_dist.py`)
- golden-fixture-driven Rivian API / MQTT / Web tests
  (`test_rivian_components.py`, fixtures under `tests/antigravity/fixtures/`)

```sh
./ci/run-fast.sh
```

### Full environment — `ci/run-full.sh`

A faithful `ubuntu:24.04` build environment that mirrors upstream
`tools/setup_dependencies.sh`. Required for compiled `opendbc`/`cereal` (CAN
parsing) tests and for **route-replay** tests:

- opendbc Rivian car-port tests
- `scorerd` replay tests (`test_scorerd_replay.py`) fed by a captured route

```sh
./ci/run-full.sh
```

Replay route data goes under `tests/antigravity/routes/` (gitignored for
privacy — route logs can contain GPS traces). Replay tests **auto-skip** when no
route is present, so the fast gate is never blocked by missing hardware data.
See [`tests/antigravity/routes/README.md`](tests/antigravity/routes/README.md)
for how to capture a segment from the device.

### Tooling requirements

- **podman** (or docker) for the test harness
- **git-lfs** for large assets and submodule data
- **Node 20** for the frontend build

## Deploying to the comma 4

Deploy the **`ap`** branch (the generated, validated build) to the comma 4 —
never `main`. At a high level, point the device's openpilot install at the `ap`
branch and let it sync. You can reach the device over SSH (e.g. `ssh comma`) to
manage and inspect it.
